# OSCAL Scribe architecture and implementation decisions

## Assessment before implementation
OSCAL Lens inspected at commit f4156824e76a776c1f9bb684a103f0ec78fd0e5f. No changes are made to that repository. Reuse its engine/model detection, flattening, import traversal, alterations, parameter substitution, provenance, mapping helpers and escaped control rendering. Keep these modules byte-for-byte in src/shared/lens, with upstream regression tests and provenance; this can later become a shared package without editing Lens now. Lens explicitly does not implement complete profile resolution (merge/custom/metadata reconciliation). Its preview must not become our authoritative baseline. A pinned OSCAL CLI resolves profiles during publication; resolved catalogues and every source are retained. Lens renders the authoritative catalogue with source comparisons when unambiguous. Schemas are official version-specific NIST JSON schemas; schema validity is not compliance certification.

## Cosmos model
Container `ssps`, partition key /sspId. Current metadata/document id=current, immutable revisions id=revision:N, attestation id=attestation:UUID, audit id=audit:UUID share the SSP partition. A transactional batch conditionally replaces current (ETag) and creates revision/audit, preventing lost updates and partial history. ACL changes and attestations also use conditional batches. Access is checked against current ACL before any historical read. List queries are server-built and parameterized, scoped to owner/ACL unless Security. Archive retains history.
Container `content`, partition key /releaseId. Immutable content releases store each source and resolved catalogue as bounded chunks (full SP800-53 catalogue exceeds Cosmos's 2 MB item limit), with SHA256, manifest and versions. A separate `active` pointer changes only after validation, resolution and full upload; failed publication never advances it. Historical releases remain addressable. Functions identity has container-scoped SSP read/write and published content read-only. Separate `staging` and `audit` containers also use /releaseId: staging is writable by the runtime, while the audit custom role allows item creation and metadata reads only. AppAdmin-only routes manage the staged library and append audit records, while publication remains restricted to the controlled pipeline; no HTTP route changes immutable releases or the active pointer. The library uses a shared registry ETag for dependency checks and chunked source storage. Normal and admin SSP lists and history use cursor pages and metadata projections. Raw exploration is disabled by default.

## API contract
Authenticated GET /api/me; GET /api/content (approved profiles/components); GET /api/content/{release}/{profile} (resolved baseline).
GET/POST /api/ssps; GET/PUT /api/ssps/{uuid}; POST /api/ssps/{uuid}/archive; POST /api/ssps/{uuid}/share; GET /api/ssps/{uuid}/revisions[/{number}]; POST /api/ssps/{uuid}/attest; POST /api/ssps/{uuid}/validate.
Create accepts profileId, releaseId and systemName. Update accepts only oscal plus If-Match revision token. Dedicated operations handle ACL/archive/attestation. 401 missing identity, 404 inaccessible object, 403 insufficient access, 409 conflict, 422 invalid OSCAL. Maximum request 1 MB, depth 64 and bounded node count. No arbitrary URLs/queries accepted.

## Entra and authorization
Single-tenant SPA app registration with authorization-code + PKCE (MSAL); API access tokens cryptographically verified for tenant issuer, API audience, delegated scope, expiry and signature via tenant JWKS. API never trusts browser identity headers or supplied owner/roles. Enterprise assignment required; application roles User, Security and AppAdmin. Immutable tid/oid identities. The SPA requests access_as_user scope and uses bearer tokens on /api; no client secret or local password. Static Web App links a separately managed Function App; JWT validation remains mandatory even for direct Function URLs. Shared canRead/canEdit/canShare/canAttest/canAdminister checks every operation. Owners and Security manage shares/attest; editors modify content only. SSP system roles never grant application permissions.

## Terraform resources
An administrator-owned resource group hosts Standard Static Web Apps (required for linked Functions), a Linux Function App, separate host and executable-package storage accounts, managed identity, Cosmos serverless database, container-scoped data roles, Log Analytics/Application Insights, Entra objects and the SWA backend link. Shared storage keys and Cosmos local authentication are disabled. Runtime package access is read-only. Continuous Cosmos backup and a deletion lock protect the database; the lock does not prevent item deletion.

The test profile retains Y1 Consumption and public Entra-authenticated data endpoints. Work dev uses EP1 Premium, VNet integration, private Cosmos/storage endpoints and private DNS; the linked Function API remains public and verifies JWTs. State has a separate public Entra-only endpoint with versioning, soft deletion and a lock. See [work dev](work-dev.md) for private-agent and identity prerequisites and the remaining production decisions.

## Assumptions and deployment decisions
The demo offers one seven-control worked profile selected from the pinned official SP800-53 Rev5 catalogue, with assigned ODPs and added statement context. Original Low/Moderate profiles are retained as reference sources rather than demo choices. Publication requires the separate explicit demo operation. Fictional SOC covers centralized logging, monitoring, incident response and threat monitoring; coverage is explicitly partial with system responsibilities. No compliance claim. Default UI has no sample data or mock authentication; offline demo server binds loopback only and is separate from production Functions.
Azure tenant/subscription, region, budget and initial user assignments require user input before deployment. Azure DevOps organization/service connections require account setup; scripts and pipelines are prepared first. No major architectural substitution is proposed.


## Component implementation editing

The SSP holds one requirement per baseline control. Component-specific descriptions, remarks and native `implementation-status` fields live in requirement/statement `by-components` entries. System is the default SSP-local component; additional local components support separate Windows/Linux implementations without duplicating baseline controls. Published components carry source links and blue origin styling, not a custom Inherited status.

Shared implementation helpers validate copy/move batches before mutation, preserve destination work, allocate independent UUIDs for copies, and calculate completion across every assigned component. Imports run on selection; ordinary view/save operations never reimport templates or restore moved assignments. The API persists these changes through the existing versioned SSP save endpoint and validates the same OSCAL schema and references. See [control workspace](control-workspace.md) for behaviour and maintenance details.

App Admin infrastructure is defined in Terraform and assigned through `app_admin_user_ids` in the protected pipeline configuration. SSP purges freeze the current record with its ETag, delete historical records in bounded batches, and remove current last. See [admin setup, storage and reference rules](app-admin.md).
